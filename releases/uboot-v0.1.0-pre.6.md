## 相对 pre.5 的变化

本版集中修复救援页「固件更新」的问题，都来自用户反馈。

- **HW-D（NX30）ECC8 机器写不进任何东西**：上传固件后显示「完整读回校验未通过」，「U-Boot 更新」同样失败，闪存其实没有被改动。原因是 HW-D 的写入流程固定按 ECC4 打开，而 NX30 R005 以后出厂的 GD5F1GQ5REYIG、FM25LS01 是 ECC8。现在按本机实际的 ECC 写入，ECC4 和 ECC8 都可以。
- **原厂固件包在大多数主板上被拒**：例如在非 HW-A 主板上上传官方 `RC3000V100R013L01.bin`，显示「固件包不支持，或完整 UBI 系统镜像结构无效、不完整」。以前 HW-B/C/D 只认 RT3000 的包，HW-A 不认 RW3000，NX30 的包在哪块板上都不认。现在四类主板都接受全部 47 个官方包：NX30 R007–R012、RC3000 R001–R013L01、RT3000 R001–R015、RW3000 R002–R012。只认逐字节一致的官方文件。
- **支持 QSDK 格式的升级包**：例如集客 N3000 / N3000V 的固件。只取出包里的那一个 UBI 系统镜像写入所选的槽，包里自带的刷机脚本不会执行。也兼容这类固件里字段顺序不同的 SquashFS。
- **显示固件是为哪个平台编译的**：校验通过后，页面列出固件内核支持的板型配置（如 `config@mp02.1`、`config@mp03.1`）和 CPU 架构，并与本机比较。不匹配时只显示提醒，不会拦截写入；写入不匹配的固件，设备可能启动不了，但救援页始终可以进入。
- **报错更准确**：
  - 不在名单里的 H3C 原厂包（版本未收录或文件被改动）提示「这个文件不在救援系统的白名单里」，不再说 UBI 结构无效。
  - 不认识的文件格式提示「文件格式不支持」。
  - 写入失败时说明停在哪一步、闪存是否已被改动，并附错误码：擦除前被拒绝时闪存原样未动；擦除或写入中途失败时目标槽已不完整。
- 去掉了「板型身份未验证，不属于已识别 OEM 包」这句提示；启动日志里打印真实的板型名称。

双系统分区表、大分区、U-Boot 更新等其他行为与 pre.5 相同。

## 从 pre.3、pre.4 或 pre.5 升级

1. 进入救援页（断电后按住 Reset 再通电），电脑用网线接 **LAN** 口，打开 `http://192.168.10.1`。
2. 在「U-Boot 更新」上传与本机对应的 `appsbl.mbn`（硬件组与 NAND 型号、ECC 与原来选的相同），确认写入。两份 APPSBL 会一起更新。
3. 断电重启，确认能正常进入系统。

救援页只接受与当前运行版本同一硬件组、同一 NAND 配置和 ECC 的构建，选错会被拒绝。不需要重刷系统固件。

**HW-D 的 ECC8 机器**：旧版的「U-Boot 更新」在这类机器上也会失败（就是本版修复的问题），请改用 RAM 救援版：在旧救援页的「网页终端」上传本版对应的 `ram-rescue.elf`，执行 `bootelf ${fileaddr}`；RAM 救援版启动后会打开新的救援页，再在新页面的「U-Boot 更新」写入 `appsbl.mbn`。步骤与 [pre.3 说明](uboot-v0.1.0-pre.3.md#从旧版升级)相同，只是不需要再刷固件。

**比 pre.3 更旧的版本**（pre.1、pre.2，BootBridge pre.1–pre.6 安装的 U-Boot）：按 [pre.3 说明](uboot-v0.1.0-pre.3.md#从旧版升级)的步骤升级，只是把文件换成本版的 `ram-rescue.elf` 和 `appsbl.mbn`；升级后同样要再刷一次固件。

**还是原厂系统的设备**：用 [BootBridge](https://flyfish-go.github.io/H3C-NX30-Uboot/) 安装。BootBridge v0.2.0-pre.3（规则 BB2-R3）安装的是 pre.5，装好后按上面的步骤升级到本版（HW-D ECC8 机器用 RAM 救援版）。

## 验证状态

- **离线**：84/84 个候选与 84/84 个 RAM 救援版构建通过；同一候选的两个版本身份一致；二进制中无构建机路径，嵌入的源码提交为 `a67e4f63`。用真实的校验处理函数逐个验证了全部 47 个官方包，并覆盖被改动的原厂包、未知格式两种报错；另有 QSDK 升级包拆包、厂商 SquashFS、平台识别和页面提示的主机测试。
- **实机**：

  | 样机 | 候选 | 本版测试内容 |
  |---|---|---|
  | HW-A | W25N01GWZEIG ECC4 | 从 pre.5 经「U-Boot 更新」升级（两份 APPSBL 与发布文件一致），冷启动显示新版本并正常进入系统；RAM 救援版下校验 RC3000 R013L01、NX30 R012 通过，被改动的包给出新报错；此前同一分支的构建写入 RW3000 R012 后读回一致并能启动 |
  | HW-B | GD5F1GQ5REYIG ECC8 | 此前同一分支的构建以 ECC8 写入原厂 RT3000 R005，读回一致，启动并能使用 Wi-Fi |
  | HW-D（NX30） | GD5F1GQ5REYIG ECC4 | RAM 救援版下校验 RC3000 R013L01、NX30 R012 通过，被改动的包给出新报错；此前同一分支的构建校验并写入集客 N3000 固件，读回一致 |

  实机测试用的 RAM 救援版与发布文件的构建来源相同，同一候选逐字节一致。
- **未验证**：HW-C 没有在本版上测试；HW-D 没有 ECC8 样机；集客固件写入后能否启动还没确认；其余候选只有离线构建结论。

## 已知限制

- 平台不匹配只提醒、不拦截。例如集客 AX3000F 是 ARM64 固件，可以写入，但这四类主板都启动不了。
- 原厂固件只认上面列出的 47 个官方文件；其他版本或改过的原厂包会被拒绝。
- 大分区只适合第三方系统，原厂固件在大分区下会被拒绝。
- 原厂 SBL 在异常复位后可能改用另一份 APPSBL，所以升级时两份必须一起写。
